多智能体协作架构：从对话到编排

单 Agent 的能力再强也有边界：上下文有限、专长单一、容易钻牛角尖。多智能体（Multi-Agent）把多个各有专长的 Agent 组织起来分工协作——这是从"单兵作战"到"团队作战"的升级。

为什么需要多个 Agent

  • 分工与专业化：研究员 Agent、代码 Agent、审阅 Agent 各有专长，比一个万能 Agent 更可靠；
  • 对抗与审查：让一个 Agent 生成、另一个 Agent 挑错，能显著提升质量（如代码互审）；
  • 并行提速：独立的子任务可以并行执行，缩短端到端延迟；
  • 上下文隔离：每个 Agent 只看自己负责的部分，避免单一上下文被撑爆。

四种主流协作模式

模式结构典型场景
Manager-Worker（层级）Manager 规划并分发子任务，Worker 执行并回报复杂项目拆解执行
Debate（辩论）多个 Agent 各自作答并互相反驳，最终裁决事实核查、方案评审
Orchestrator-Plugins（编排器）一个编排器调用一组工具化 Agent客服、RAG 问答流水线
Swarm（群体）Agent 之间直接传递消息，无中心调度松耦合协作任务

通信机制

  • 消息传递：Agent 之间直接发消息（AutoGen 的对话式）；
  • 共享黑板：所有 Agent 读写同一个状态对象（LangGraph 的 State）；
  • 结构化调用：像 Function Calling 一样，把"调用另一个 Agent"也注册成一个工具——Agent 互相"当工具用"。

框架对比

框架协作形态特点
AutoGen对话式多 AgentAgent 之间自由对话、可切换发言者

与 MRKL 的关系

MRKL 的"专家模块"是静态的（知识库、计算器）；多智能体系统把专家模块动态化——每个 Agent 就是一个带推理能力的专家。Router 的角色升级为 Manager/Orchestrator，循环的每个节点都可能是一个完整的小 Agent Loop。可以说：多智能体 = MRKL 的组织思想 + ReAct 的执行协议 + 多个 Loop 的组合。

挑战：成本、收敛与死循环

  • token 成本放大：N 个 Agent 互相传话，成本近似乘 N → 控制轮次上限、避免无意义寒暄；
  • 收敛性：辩论模式可能永远达不成一致 → 设置最大轮数 + 明确的终止条件（投票、时间、目标达成）；
  • 死循环 / 循环引用：Agent A 调用 B、B 又调回 A → 像单 Agent 一样需要迭代上限，最好再加循环检测；
  • 上下文放大：共享黑板如果全部可见，等于又造了一个大上下文 → 按需读写、隔离视图。

总结

多智能体不是"越多越好"，而是"合适的分工 + 明确的控制流 + 强硬的终止条件"。先想清楚谁负责什么、怎么交接、如何停止，再选框架——否则团队越大，失控越快。
